# Отчёт по лабораторным работам

**Защищённая система передачи сообщений на отечественных криптографических
стандартах**

Кафедра 304 · Информационная безопасность

---

## 1. Что сделано

Веб-система, в которой пользователь после трёхфакторной аутентификации
шифрует сообщение одним из двух методов, хранит его в базе в зашифрованном
виде и может выгрузить отчёт в PDF с электронной подписью, проверяемой
любым желающим.

Вся криптография — собственная реализация, без внешних библиотек:

| Примитив | Стандарт | Где применяется |
|---|---|---|
| Кузнечик | ГОСТ Р 34.12-2015 | шифрование сообщений (режим CTR), защита ключей сообщений |
| Стрибог | ГОСТ Р 34.11-2012 | хеширование паролей, хеш под электронную подпись |
| RSA | собственная длинная арифметика, модуль 32768 бит | шифрование сообщений, ЭЦП |

---

## 2. Архитектура: один шов

Криптография написана на C++, веб-приложение — на Python. Единственное место
их соприкосновения — консольная программа `crypto_cli`, которую Python
запускает через `subprocess.run()`.

```
   браузер
      │  HTTP
      ▼
   FastAPI (Python)  ──  SQLite
      │
      │  crypto.py  ← единственный модуль, знающий о C++
      │  subprocess.run([...])
      ▼
   crypto_cli (C++)  ──  Кузнечик · Стрибог · RSA · BigInt
```

### Контракт между слоями

```
stdout      только результат, одна строка hex
stderr      ошибки и трассировка
код 0       успех
код != 0    неуспех
```

Благодаря этой дисциплине обработка ошибок в Python одинакова для всех десяти
подкоманд и занимает три строки (`crypto.py`, функция `_run`).

Мелкие данные фиксированной длины (ключи, IV, хеши, подписи) передаются как
hex в аргументах командной строки. Данные произвольной длины — через файлы:
длина командной строки ограничена, а двоичные байты в ней не выживают.

### Почему процесс, а не DLL

Вызов через `ctypes` был бы быстрее, но передать `BigInt` через границу
невозможно: это класс C++ с `std::vector` внутри, и Python не умеет ни
создать его, ни освободить. Пришлось бы писать плоскую C-обёртку,
обменивающуюся теми же hex-строками, но уже с ручным управлением памятью.

Главное же — **изоляция процесса является свойством безопасности**. Ошибка
работы с памятью или аварийное завершение в криптографическом слое убивают
отдельный процесс, который возвращает ненулевой код; веб-сервер при этом
продолжает работать, пишет запись в журнал и отдаёт ошибку 500. При загрузке
библиотеки в адресное пространство сервера та же ошибка повредила бы память,
в которой лежат сессии всех пользователей.

## 3. Режим работы блочного шифра

`grasshopperCode()` преобразует ровно 128 бит. Сообщение пользователя имеет
произвольную длину, поэтому нужен режим работы. Выбран **CTR**
(гаммирование со счётчиком, ГОСТ Р 34.13-2015):

```
блок счётчика_i = IV (8 байт) || i (8 байт, big-endian)
гамма_i         = Кузнечик(блок счётчика_i, ключ)
шифртекст_i     = открытый текст_i XOR гамма_i
```

### Почему CTR, а не ECB

ECB шифрует каждый блок независимо, поэтому одинаковые блоки открытого текста
дают одинаковые блоки шифртекста, и структура данных остаётся видна.
Классическая иллюстрация — изображение пингвина, зашифрованное в ECB:
контуры читаются на шифртексте. ECB непригоден для любых данных, кроме
одиночного случайного блока.

### Почему CTR, а не CBC

1. **Нет выравнивания.** Последний блок гаммы просто обрезается по длине
   остатка; шифртекст равен по длине открытому тексту. CBC потребовал бы
   схему дополнения PKCS#7 и процедуру его снятия, которая обязана корректно
   отвергать некорректное дополнение. Ошибка в ней порождает атаку
   «padding oracle».
2. **Шифрование и расшифрование — одна операция**, так как XOR обратен сам
   себе. Код вдвое меньше и не может разойтись между двумя ветками.
3. **Обратное преобразование шифра не используется вовсе** —
   `grasshopperDeCode` в системе не вызывается.

### Правило, которое нельзя нарушать

Пара (ключ, IV) не должна повторяться. Если повторить:

```
c1 = p1 XOR g
c2 = p2 XOR g
c1 XOR c2 = p1 XOR p2      ← ключ сократился
```

Атакующий получает XOR двух открытых текстов без всякого ключа; для
естественного языка этого достаточно для восстановления обоих. Поэтому
для каждого сообщения генерируется новый случайный 64-битный IV, который
хранится рядом с шифртекстом (IV не является секретом).

## 4. Управление ключами

### Ключ сообщения и мастер-ключ (конвертное шифрование)

На каждое сообщение генерируется случайный 256-битный ключ. В базу он
записывается не открытым, а зашифрованным **мастер-ключом сервера**, который
хранится в файле `secrets/master.key` вне каталога веб-приложения.

Следствие: украденной базы данных недостаточно. Чтобы расшифровать хотя бы
одно сообщение, нужен ещё и файл мастер-ключа, то есть доступ к файловой
системе сервера, а не только к базе.

### Открытый текст не хранится

В таблице `messages` нет колонки с открытым текстом. Страница истории
показывает шифртекст, а расшифрование выполняется по требованию в момент
открытия записи. Система, хранящая все сообщения в открытом виде,
обессмысливает собственное шифрование.

## 5. Хеширование паролей

```
соль = 16 случайных байт, своя у каждого пользователя
h = Стрибог512(соль || пароль)
повторить N раз:  h = Стрибог512(h || соль)
в базе: соль, N, h
```

**Соль** обесценивает радужные таблицы: предвычисленный словарь годится
максимум для одного пользователя.

**Повторение** задаёт стоимость одной проверки. Измерено на машине разработки:
около 6600 итераций Стрибога в секунду. Выбрано N = 5000, то есть примерно
0,8 с на проверку пароля — обычный ориентир для интерактивного входа.
Перебор при этом дорожает ровно в 5000 раз.

Число итераций хранится **у каждого пользователя**, а не в коде, поэтому его
можно поднять в будущем, не ломая уже существующие учётные записи.

### Честное ограничение

Конструкция затрудняет перебор по **времени** (CPU), но не по **памяти**.
Argon2id дополнительно требует от атакующего гигабайты оперативной памяти,
что делает невыгодным перебор на GPU и ASIC, где параллелизма много,
а памяти на поток мало. Стрибог здесь выбран потому, что это собственная
реализованная примитива, и это защитимый выбор для учебной работы —
но он не равноценен Argon2id, и утверждать обратное было бы неверно.

## 6. Три фактора аутентификации

Фактор должен быть другой **категорией** доказательства, иначе получается
один фактор, применённый три раза.

| № | Фактор | Категория | Механизм |
|---|---|---|---|
| 1 | Пароль | то, что вы **знаете** | Стрибог с солью и 5000 итераций |
| 2 | Код из письма | то, к чему у вас есть **доступ** | 6 цифр, 5 минут, хранится хешем |
| 3 | Код TOTP | то, что вы **держите** | RFC 6238, общий секрет с телефоном |

Коды восстановления (10 штук, одноразовые) заменяют сразу факторы 2 и 3 —
на случай одновременной потери телефона и доступа к почте.

### Машина состояний входа

```
POST /login        пароль верен  -> login_flow(stage = 1), письмо с кодом
POST /login/email  код верен     -> stage = 2
POST /login/totp   TOTP верен    -> выдача сессии, процесс входа удаляется
```

**Стадия хранится на сервере**, в таблице `login_flows`; в браузер уходит
только случайный токен процесса. Каждый шаг заново читает стадию из базы и
отказывается выполняться не на своей стадии. Если бы стадия лежала в скрытом
поле формы или в cookie, атакующий, знающий только пароль, подставил бы
`stage = 3` и вошёл — и трёхфакторная аутентификация осталась бы только
на схеме. Процессу входа даётся 10 минут.

### Сопутствующие меры

- Одинаковый текст ошибки для «нет такого пользователя» и «неверный пароль»:
  разные сообщения позволяют перебором выяснить существующие имена.
- Блокировка учётной записи на 15 минут после 5 неудачных попыток.
- Не более 5 попыток ввода одного кода из письма, затем код гасится:
  шесть цифр — это миллион вариантов, перебираемых скриптом за минуты.
- Сравнение кодов и хешей через `compare_digest` (постоянное время):
  обычное сравнение завершается на первом несовпавшем байте, и по времени
  ответа можно побайтно подбирать правильное значение.
- Ограничение частоты запросов по адресу: не более 10 попыток входа
  или сброса пароля в минуту.

## 7. Электронная подпись

```
подпись  = RSA_d( Стрибог512(байты документа) )
проверка: RSA_e( подпись ) == Стрибог512(байты документа)
```

Подписывается хеш, а не документ: документ в мегабайты не поместится в один
блок RSA, а возведение в степень по модулю 32768 бит для каждого блока было бы
недопустимо медленным.

### Ловушка: подпись нельзя положить внутрь подписываемого документа

Встраивание подписи в PDF меняет байты файла, вместе с ними меняется хеш, и
подпись перестаёт соответствовать документу. Поэтому выбран вариант
с **отдельным файлом**: выдаются `message-N.pdf` и `message-N.pdf.sig`,
и подписаны ровно те байты PDF, которые скачал пользователь.

Отсюда следует второе решение: готовый PDF и его подпись сохраняются на диск
и при повторном скачивании отдаются те же самые байты. Если собирать PDF
заново на каждый запрос, в него попадёт новая дата создания, байты разойдутся,
и подпись к ранее скачанному файлу перестанет проходить проверку.

### Страница проверки

Открыта всем, включая гостей: для проверки нужен только открытый ключ.
Загружаются два файла, выводится результат и то, что именно сравнивалось.
Подпись, которую никто не может проверить, — это украшение, а не подпись.

### Ограничение

Используется «учебная» RSA без схемы заполнения — ни OAEP для шифрования,
ни PSS для подписи. Практические следствия:

- шифрование **детерминировано**: одинаковые сообщения дают одинаковый
  шифртекст, то есть утекает информация о повторах;
- шифртексты **перемножаемы**: `c1·c2 mod n` расшифруется в `m1·m2`;
- подпись без PSS уязвима к некоторым экзистенциальным подделкам.

См. RFC 8017. Это осознанный выбор ради демонстрации самой арифметики RSA,
а не недосмотр.

## 8. Разграничение доступа

| Роль | Права |
|---|---|
| Гость | открытые страницы, проверка подписи |
| Пользователь | шифрование разрешёнными методами, своя история, PDF с подписью |
| Администратор | всё перечисленное, плюс переключение методов, просмотр всех сообщений, создание учётных записей |

Реализация:

- Роль **никогда не хранится в cookie**. В cookie лежит только случайный
  токен сессии; роль читается из базы при каждом запросе.
- Одна зависимость `require_admin` на все административные маршруты.
  Забытая проверка на одном маршруте — самая частая уязвимость в учебных
  проектах, поэтому проверка одна и подключается явно.
- Выборки сообщений ограничены `user_id` **из сессии**, а не из URL.
- Чужое сообщение возвращает **404, а не 403**: код 403 подтвердил бы,
  что запись с таким номером существует.
- Переключатели методов проверяются повторно в обработчике отправки формы:
  то, что форма предложила только разрешённые варианты, ничего не
  гарантирует — POST-запрос можно отправить напрямую.
- Первый администратор создаётся консольным скриптом `seed_admin.py`,
  а не веб-маршрутом. Открытый маршрут «сделай меня администратором»,
  который забыли удалить, — это полная компрометация системы.

## 9. Прочие меры защиты

| Мера | Реализация |
|---|---|
| SQL-инъекции | все значения передаются только параметрами `?`; f-строк внутри `execute()` нет ни одной |
| XSS | автоэкранирование Jinja2 включено, фильтр `\|safe` не применяется к пользовательским данным нигде |
| CSRF | токен в сессии, сверяется при каждом изменяющем состояние POST |
| Кража сессии | cookie `HttpOnly`, `SameSite=Lax`; `Secure` включается при работе по HTTPS |
| Смена пароля | все существующие сессии закрываются |
| Журналирование | вход (успех и неудача), шифрование, выгрузка PDF, проверка подписи, все действия администратора |

Журнал — это про **обнаружение**, а не про предотвращение: он отвечает на
вопрос «что произошло», когда защита уже не сработала. Он же используется для
подсчёта частоты попыток: отдельная таблица счётчиков не нужна, а по журналу
видно, откуда взялась блокировка.

## 10. Производительность

Измерено: WSL Ubuntu 22.04, g++ 11.4, оптимизация `-O2`.

| Операция | Время |
|---|---|
| Кузнечик CTR, 10 КБ | 0,05 с |
| Стрибог, 1 МБ | 0,69 с |
| Хеш пароля, 5000 итераций | ≈0,8 с |
| RSA-32768: шифрование | 0,02 с |
| RSA-32768: проверка подписи | 0,71 с |
| RSA-32768: **расшифрование и подпись** | **16 с** |
| RSA-32768: генерация ключа | 912 с |

Асимметрия объясняется выбором экспонент: открытая `e = 65537` имеет 17 бит,
закрытая `d` — все 32768. Возведение в степень по модулю требует числа
умножений, пропорционального длине показателя, поэтому операции с `d`
примерно в две тысячи раз дороже.

Ускорить их можно китайской теоремой об остатках (вычислять по модулям `p`
и `q` по отдельности, что дало бы выигрыш примерно вчетверо), но для этого
нужно сохранять `p` и `q`, которые текущий генератор отбрасывает после
вычисления `d`.

На соответствующих страницах интерфейса указано, что операция занимает
около 16 секунд, чтобы ожидание не выглядело зависанием.

## 11. Проверка корректности

### Контрольные векторы стандартов

`crypto_cli selftest` — 22 проверки:

- все десять раундовых ключей Кузнечика, выведенные из мастер-ключа,
  сверяются со значениями из ГОСТ Р 34.12-2015, приложение A;

- Стрибог 256 и 512 бит на сообщении M1 (63 байта, один блок) и

Проверка **всех раундовых ключей**, а не только шифртекста одного блока, —
принципиальна: именно так была обнаружена ошибка в исходной развёртке ключа
(см. раздел 12).

### Сквозные тесты

- `ЗИ_ЛР/test_cli.sh` — 30 проверок контракта CLI, включая все пути отказа:
  короткий ключ, неверный ключ, слишком длинное сообщение, подделанный
  документ, подделанная подпись, ошибка не в stdout.
- `web/test_app.py` — 47 проверок всего пути пользователя, включая попытки
  обхода: пропуск стадии входа, подделка CSRF-токена, чтение чужого
  сообщения, прямой POST с отключённым методом.

## 12. Две ошибки, найденные и исправленные в ходе работы

Обе проходили контрольные векторы ГОСТ и обе сделали бы систему
неработоспособной. Они описаны здесь, потому что их разбор показателен.

### 12.1 Кузнечик игнорировал переданный ключ

Функция `grasshopperCode()` вызывала `generateKeysCorrect()`, которая
**жёстко задавала десять раундовых ключей из контрольного примера ГОСТ и
полностью игнорировала аргумент `key`**. Контрольный вектор проходил именно
потому, что в код были вписаны его собственные раундовые ключи. При любом
другом ключе результат оставался тем же — то есть все сообщения системы
шифровались бы одним общеизвестным ключом.

Исправлено: реализована настоящая развёртка по ГОСТ Р 34.12-2015, п. 4.4 —
четыре пары ключей, по восемь применений функции F на пару, константы
C₁…C₃₂. Корректность подтверждена сверкой всех десяти выведенных ключей
со значениями стандарта.

**Вывод для методики проверки:** контрольный вектор на выходе шифра не
проверяет развёртку ключа, если развёртка подменена константами из того же
вектора. Проверять надо промежуточные величины.

### 12.2 Стрибог хешировал только 63 байта

Драйвер содержал цикл `for (int i = 0; i < 1; i++)` — ровно один блок — и брал
длину сообщения из `BigInt::bitLength()`, которая теряет ведущие нулевые
байты. Контрольное сообщение M1 имеет длину 63 байта и умещалось в один блок;
всё более длинное хешировалось неверно. Это сделало бы невозможными и
хеширование паролей, и подпись документов.

Исправлено: реализован полный многоблочный алгоритм по ГОСТ Р 34.11-2012,
раздел 8, со сложением контрольной суммы Σ **по модулю 2⁵¹²** (обычное
сложение `BigInt` наращивает девятое слово при переносе, и оно незаметно
портило бы итоговый хеш). Корректность подтверждена на векторе M2 (72 байта,
два блока).

## 13. Известные ограничения

Перечислены сознательно и полностью.

1. **RSA без схемы заполнения.** Детерминированное шифрование, свойство
   мультипликативности, подпись без PSS. Требуется OAEP и PSS (RFC 8017).
2. **Функция выработки ключа из пароля не является памяте-затратной.**
   Argon2id дополнительно нагружал бы атакующего по памяти.
3. **Нет HTTPS.** Демонстрация идёт по HTTP, поэтому флаг `Secure` у cookie
   выключен. При наличии сертификата включается одной настройкой.
4. **Нет оптимизации по китайской теореме об остатках**, отсюда 16 секунд
   на расшифрование и подпись.
5. **SQLite допускает одного пишущего.** Для учебной демонстрации достаточно,
   для нагрузки — нет.
6. **Мастер-ключ хранится в файле на той же машине.** В промышленной системе
   он жил бы в аппаратном модуле (HSM) или в менеджере секретов.
7. **Коды восстановления понижают стойкость до одного фактора плюс код.**
   Это сознательный компромисс в пользу доступности; альтернатива —
   обращение к администратору.
